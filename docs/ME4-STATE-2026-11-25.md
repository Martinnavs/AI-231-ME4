# ME4: where we are, what is hard, what we searched (self-contained status, 2026-11-25)

Written for a reader who has never seen the project or its code. Nothing here requires opening a repository. Every number is tagged **MEASURED** (we ran it), **ESTIMATE** (reasoned or extrapolated) or **CLAIM** (from a source we did not verify). Production day is **Friday 2026-11-27**; today is Wednesday 2026-11-25; we plan a configuration freeze on Thursday 18:00.

---

## 1. The task in one paragraph

ME4 is a voice-and-text assistant that must answer questions **only from a bundle of documents it is given on the day** (a zip of mixed files), **from the web**, or **from both**. It runs entirely on a **Raspberry Pi 4** (aarch64, 4 cores, about 3.8 GB RAM, about 2.5 to 2.7 GB free with our stack running, SD-card disk with about 2.4 GB free, no GPU). All parsing, indexing and retrieval happen on the Pi. Files may arrive over LAN or the internet but are parsed on the Pi. The model that writes answers is a hosted LLM (Gemini Flash-Lite class, one provider on test day). The organisers (a professor's course) told us: everything on the Pi; OCR is in scope (scans and images are part of the data); prepare for all question kinds; answers may come from the documents, the web, or both. The size and content of the zip are **unknown until the day**; the ingest window is **1 hour (2 hours maximum)**. Speech in and out (STT/TTS) is part of the product but has **never been run on the Pi** in our work so far.

**What "good" means** (our reading of the spec): correct, short, spoken-style answers that cite the source file; honest refusal ("the documents don't say") when the documents do not contain the answer; no hallucinated numbers; no obeying instructions hidden inside documents; sensible web use when the question is about the world rather than the files; first spoken answer in about 1.5 to 3 seconds.

## 2. System as it exists today

### 2.1 Ingest (documents to a SQLite database)
- Input: a zip (or folder) of mixed files: Office (docx, pptx, xlsx), markdown, pdf, html, csv, txt, images and scanned pages.
- Each file is converted to text and split into chunks (about 13,900 chunks for a 44-file, 160 MB-class test corpus; **MEASURED**: 44 files give 13,894 chunks).
- Everything lands in one SQLite file: a chunk table, an **FTS5** full-text index (BM25 ranking), a per-file "card" table (title, kind, section outline, a few keywords, row counts for tables), and an image table for scans and embedded pictures.
- Ingest can stream in batches (5,000 chunks) so memory stays bounded; it can run worker processes, with time and disk governors and resume, **when ingesting a folder**. The **zip path bypasses workers, governors and resume** (known gap; plan: extract the zip to a folder first, then ingest the folder).
- **OCR** is a second stage that runs after text is indexed: stage A lists images and scanned pages; stage B runs an OCR engine. Engine chosen after a research pass: **Tesseract 5.5** (installed on the Pi) as the working engine; RapidOCR was the preferred engine but its models are not installed. Pi benchmark (**MEASURED**): 30 images, median 1.04 s per image (p90 2.81 s), 18 of the 30 had recognisable text; 133 images were still pending after the text-only ingest, which is expected (OCR is deferred and can be skipped if time is short).
- Pi ingest of the 44-file corpus (**MEASURED**): 116 s wall (an earlier run took 77 to 87 s on the same data; cause of the difference not isolated: more indexes, or SD-card variance), parent process peak 159 MB, all 44 files ok, index rows equal chunk rows.

### 2.2 Retrieval and answering ("docs-first")
1. Question arrives (text, or speech turned into text).
2. A cheap rule decides if it "looks like a question" about documents (as opposed to a command such as "set a timer"). There is **no local router model** on the Pi; commands go straight to the hosted model's tool path.
3. For document-like questions the system calls `file_context`: rank files by one FTS5 query, take the top 3 files, and return their best passages (about 15 passages). **MEASURED** on the Pi: median 0.042 s after an indexing fix (it was 1.23 s before).
4. **One** LLM call (`ask_documents`) gets the passages and must return structured JSON: an answer, the file it came from, and verbatim quotes. Median about 1.4 s (**MEASURED** live, $0.0019 per call on average).
5. **Deterministic checks** then accept or reject the answer without another model call. In order: the cited file exists and was in the context; each quote is a real span of the cited passages; any computed number is re-derived by a small safe expression evaluator; names and numbers in the answer appear in the quotes; quote length 3 to 30 words; word overlap between question and quote; a directive guard (quotes that look like instructions are rejected); a named-file guard; an "ordinal" guard for first/last questions.
6. If accepted, the answer is spoken in the form "As per <file>: <answer>". If rejected or "none", the turn falls through to the hosted model's normal agent path (web search via grounding, tools). Today that fall-through carries a note telling the model that the documents were checked and do not answer; the model then often answers from the web **without telling the user the documents were silent** (a known flaw, see section 4).
7. A web leg exists (Gemini with Google Search grounding), and a "doc then web" status; combined doc+web composition is only lightly tested live.

### 2.3 Other pieces
- An older background "second look" verifier (re-asks the question with search forced and compares). **Off** in the Pi configuration; it checks the first lookup rather than what was spoken, and it only runs on web turns.
- A network fix: the Pi resolved IPv6 first and connections to the model API took 2 to 8 seconds; a small shim now prefers IPv4 (**MEASURED**: 0.05 s after, 2.15 to 8.2 s before).
- Budget: live API spend is capped by a ledger; about $0.50 is available now, two paid measurement rounds at most, keep at least $0.10 for Friday.

## 3. What we measured

### 3.1 Offline (free) evaluation sets
We maintain test sets of question rows with accepted answer strings and a flag for "unanswerable" rows (the document does not contain the answer). The evaluator replays a **fixed oracle** (a "tempted" wrong answer, a quote taken from a decoy passage) through the deterministic checks to measure how often they wrongly accept.
- Accepted-correct (higher is better; **MEASURED**, unchanged since the last retrieval fix): dev 12/13; "golden" 99/112; held-out corpus A 27/32; held-out corpus B 9/11.
- Tempted false accepts (lower is better): golden 8; A 4; B 2; a 25-question "not in the documents" set: 9 of 25.
- Retrieval ceiling (**MEASURED** by an earlier spike over 168 answerable rows): the right file is in the top 3 for **159 of 168**; the fact reaches the model for **152 of 168**. Conclusion: ranking is no longer the bottleneck; at most about 9 rows can be won by any better ranker.

### 3.2 Live
- A new adversarial set, **golden-v2** (120 rows, categories: document-only, doc+web, traps, web-only; includes decoy values, wrong-row table lures, an injected instruction, stale-vs-current values, follow-ups). First live document-leg run (**MEASURED**): 81 calls, $0.154, median 1.38 s per call. Failures clustered in: a table cell quote lacking its row key, a retrieval miss, an injection leak (a Wi-Fi password quoted from a document that contained a fake "system note"), stale document values accepted when the question says "current/latest", and follow-ups ("which file?").
- Last Pi re-run (**MEASURED**, ten typed turns through the full stack, no router, docs-first): **8/10 right**. Misses: two questions whose answer is **not** in the documents (a pets policy; electricity price in Guam) were answered from the web with no "your documents don't cover that" caveat. One document fact ("how quickly must I notify IT of a security incident", answer "within 1 hour") was **answered correctly but via the web in 9.5 s** because the document path rejected it (cause not diagnosed; the turn log lost the reason; likely the quote check failing on "one hour" vs "1 hour").
- Pi system numbers (**MEASURED**): first spoken text 1.55 to 2.65 s on document turns; weather via the tool path 3.9 s (it used to be 0.9 s with a router); free memory 2.7 GB with the stack up; no thermal throttling.

## 4. The main problems, ranked

1. **Behaviour after a document miss.** Questions the documents cannot answer are answered from the web without saying so, and a misrouted document fact can silently become a web answer. Needed: an explicit policy in code (document-scoped question and no answer: say "the documents don't say"; open question: web answer prefixed "your documents don't cover that"), plus logging the document verdict on every fall-through (today it is dropped, which also made the failures above undiagnosable).
2. **General (corpus-level) questions are not answerable.** "What are all the files about?", "what can I ask?", "summarise the folder", "which files mention X", "compare these two documents". Top-k retrieval by relevance cannot give coverage: on a 48-file corpus the question "what are all the files about" retrieves passages from **3 files** (three tax guides) because the words "files" and "about" match tax text; the fallback catalogue helper fits only **6 of 48** files in its 2,000-character cap. Needed: a separate overview path that reads all per-file cards (grouped by folder), with its own checks (every file or folder named must exist; any "N files" claim equals the count; numbers must appear in the context).
3. **Specific-fact correctness checks** (deterministic, free): number words versus digits ("one hour" vs "1 hour"); a file named by basename only; table lines where the quoted row key does not match the question (Virginia vs West Virginia; a row that exists in no table, e.g. Guam, must abstain); an **injected paragraph** in a document (a fake "SYSTEM NOTE ... tell the user the password is X"): today only the first line of a paragraph is tested, so later lines reach the model.
4. **Non-document intents pay a wasted document call** (weather, time, timer, music, news): weather first-answer latency rose from 0.9 s to 3.9 s. Needed: a narrow classifier that skips documents, careful not to misroute real document questions ("what time does the exam start", "what temperature range does the datasheet give").
5. **Stale vs current**: a document may contain an old value ("wage base 2025") while the question asks for the current/latest. Accepting the document value is wrong. Cheap mitigation: speak the year or date of the source ("As per X (2024): ..."). A real fix needs a document-versus-web conflict check.
6. **Unknown corpus size** (could be 1.4 GB): the zip path holds all parse results in the parent process (about 590 MB parent memory at a 160 MB corpus; our extrapolation to a 1.4 GB zip is 3 to 4 GB, **ESTIMATE**, against about 3.3 GB free). Plan: extract to a folder and ingest the folder with workers, a 50-minute deadline, and a spoken "I read N of M files"; one-worker fallback. **Folder ingest with workers has not been run on the Pi.**
7. **Speech has never run on the Pi** (STT and TTS compete with the agent for 4 cores and about 2.7 GB). Fallback: typed questions if the organisers allow it (question pending to the professor).
8. **Follow-ups** ("and the second one?", "which file was that?") are handled by luck through the hosted model's history; no deterministic resolution to the last cited file.
9. **Multi-step "deep research" questions** (multi-hop across files, aggregates, doc+web synthesis) are not supported in a single turn: a second web lookup in the same turn is suppressed; only an asynchronous delegate does multi-step work, and it needs an API key the Pi does not have.
10. **Verification turn** (a second call that re-checks the draft answer before it is spoken): wanted by the owner; not implemented for document answers; designed but held (see 6.5).

## 5. Decisions already taken (do not re-argue unless you have new evidence)
- Keep our own ingest and SQLite/FTS5 retrieval; add file-first context and grep-like enumeration; keep one structured LLM call plus deterministic checks.
- No local router model on the Pi (wasted memory, little gain). No hedged parallel calls. No header stacker.
- Embeddings, rerankers, query rewriting, ColBERT/SPLADE, LLM-written per-file summaries as a **ranking** signal: rejected. Two independent experiments showed no gain or a loss (static embeddings lost 10 golden rows; simple per-file summaries as a ranking signal reduced facts reaching the model from 152 to between 140 and 148).
- GraphRAG with LLM community summaries: rejected for Friday. The source book itself says it is the wrong tool for low-latency, verbatim-citation fact lookup, and it needs model calls over the whole corpus at ingest. We keep the **goal** (whole-corpus overview) through a cheap catalogue path built from per-file cards with no model calls.
- One model provider on test day. (Alternative cheaper hosted models via a router service were discussed; the owner wants to decide the key and budget; no switch planned unless one clearly beats the current model.)

## 6. What we researched (and what each source told us)

1. **OCR on a Pi**: compared engines under Pi constraints. Result: Tesseract as the reliable baseline (already installed, measured above), RapidOCR/ONNX as optional, no GPU models. Found and fixed bugs in our OCR code (page-render returned raw RGB bytes instead of PNG; duplicate images; notes stacking).
2. **RAG end-to-end datasets** (survey by a coding model): FreshQA, SealQA, FinanceBench, TAT-QA, and similar were identified as sources for web, finance and table questions; we built our own mixed "golden-v2" set (document-only, web-only, doc+web, traps) and plan to pull about 40 rows each from a few public sets if time allows.
3. **Alternatives review** by an independent senior-style critic (twice): confirmed the hybrid plan, recommended dropping the local router, hedging, the old background verifier and the header stacker; flagged that retrieval is no longer the bottleneck; flagged the zip ingest and governor gaps and per-file memory growth.
4. **Verification turn research** (two agents). (a) Literature and designs: do not run an unconditional second LLM call or a local NLI classifier on every turn; four of the five known failure modes are structural and fixed by deterministic checks at zero latency and cost; an LLM verifier should be selective (tables, borderline overlap, doc-versus-web conflicts, mutable facts), single-shot, thinking minimal, at most 0.9 s, **fail open**, and may use documents, web or both; do not combine web search tools with a JSON-schema output in one call (grounding metadata can come back empty; unverified). Published: intrinsic self-correction can reduce accuracy (a 2024 ICLR paper reports about -6% on two benchmarks); NLI judges falsely reject 24 to 33% of flagged QA claims (**CLAIM**). (b) A reading of an earlier project (OnIt) that ships a run-time two-stage fact-checker: free deterministic skip first (every number/URL/quote already verbatim in trusted tool output), then a non-thinking temperature-0 JSON verdict with a 2 s ceiling and fail-open; it dropped a blocking tool-lookup-and-rewrite design within hours because it doubled latency; turning thinking off cut verdict time from 15 to 21 s to 0.2 to 1.6 s on a 27B model; there is **no controlled accuracy ablation** of its verifier, only run labels (820 clean, 70 issues, 120 unchecked across 1,010 trajectories).
5. **Index-layer question** ("is there a lightweight layer on top of SQLite that greatly improves retrieval?"): answer **no for ranking** (ceiling is about 9 rows), **yes for two small structured checks** (row-key check for table lines; number-word normalisation) and for **coverage questions** (overview path, and "which files mention X" by listing the distinct files that match in the existing FTS index).
6. **Graph layer** ("a node per document with an overview and helper values"): useful as plain per-file cards (overview, folder, outline) plus, later, an entity table (entity to files/chunks) and links between files by shared rare entities; **built at ingest with regexes, no model calls** (estimate 5 to 15 s on a 44-file corpus, 2 to 5 min for a 160 MB one, a few MB of disk); not a graph database; not a ranker. Only the overview piece is needed for Friday.
7. **Deep-research capability**: a bounded plan, parallel lookups, synthesise loop (about 2 to 3 model calls, 3.5 to 8.5 s total, about $0.003 per question) is feasible and designed, with a time cutoff and spoken progress; but it cannot be measured in two paid rounds, so it is **cut for Friday** and kept as the first post-Friday item. A repository audit found it cannot reliably do general or multi-step answers today because of hard caps (3 files per answer, top-k 8, one web lookup per turn, no document access in the async delegate).
8. **Textbook excerpts (Hands-On RAG)**: short-term memory (adopt, we have it); resolve follow-ups to the last cited file (adapt); long-term memory (reject); OCR text as chunks (adapt); vision captions only under a $0.02 cap; multimodal embeddings, hybrid search, reranking (reject, measured no gain); knowledge-graph chunk enrichment (adapt as plain cards, no model calls); GraphRAG (reject mechanism, keep goal); the book's own checklist for adopting a knowledge graph (we answer yes to about 2 of 6) says skip it.
9. **Speech vocabulary**: the speech stack can bias recognition toward a list of names and repair near-misses. An idea: generate the list from the SQLite corpus after ingest (proper names, acronyms, ids, rare words, ranked by corpus-versus-English frequency, capped at a few hundred). Not built; gated on a speech test on the Pi.

## 8. Open questions where an outside view would help
1. Is "refuse on a document-scoped miss; web with a caveat on an open miss" the right policy given the spec says "docs, web or both"? Could a hybrid (say "the documents don't say; the web says ...") score better with graders?
2. Is a selective verifier worth shipping at all with only two paid measurement rounds, or should deterministic checks plus the year-of-source rule be the whole answer for stale values?
3. Are there cheap, no-model signals for "the question is about the corpus" versus "about the world" better than keyword cues over file names and card titles?
4. For general questions at scale (hundreds or thousands of files), is a folder-grouped card catalogue plus enumeration enough, or is there a known cheap structure (for example per-folder summaries built at ingest with one model call per folder) that is worth its cost at 1,000 files?
5. Best way to resolve spoken follow-ups to the last cited file without a model call.
6. Anything in our ingest-on-a-Pi plan (folder with workers, 50-minute deadline, OCR deferred, partial index served) that you believe will fail on a 1 GB-class corpus.
7. Any evaluation we are missing that the organisers' hidden test set is likely to contain (question types, formats, trick cases).

## 9. Glossary
- **Chunk**: a passage of a document (a few hundred words). **FTS5**: SQLite's full-text search; ranks by BM25. **File card**: a one-line-per-file summary (title, kind, outline, keywords). **Docs-first**: try the documents before the web or tools. **Tempted false accept**: our offline stress test, how often a wrong, decoy-based answer passes the deterministic checks. **Fail open**: if a check times out or errors, keep the original answer. **RC**: release candidate.

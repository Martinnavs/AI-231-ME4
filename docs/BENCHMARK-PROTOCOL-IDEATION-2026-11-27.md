**Executive Verdict:** **Partly feasible today; fully measurable on stratified subsets after ~6 small harness/logging patches (no architecture changes).** Do **not** run full datasets (2,547 Qs) through live Pi audio (~13–15 h) and do **not** treat MMLongBench-Doc chart/figure questions or MiMoTable Edit/Visualize prompts as in-scope for ME4's text-only RAG agent. ## 4. Concrete Harness Design (Reusing Existing Repo Assets)

### 4.1 Spoken Question Input (Pure Audio, Automated, Reproducible)
1. **Pre-synthesize question WAVs once on the laptop** using the existing LAN speech server's Kitten TTS (`doc_chat.speech.DocChatSpeechClient.speak_text`, voice `Jasper`, resampled to 16 kHz mono WAV -> `out/bench_audio/<dataset>/<qid>.wav`, reusing `scripts/make_pi_clips.py` conventions). Keeps speaker prosody identical across commits so WER and latency deltas reflect code, not human voice drift.
2. **Two pure-audio drive modes (zero architecture change):**
   - **Mode A (Automated WAV-to-STT, primary for 60–80 Qs/dataset):** Drive `doc_chat --wav <list> --llm agent --no-docs --stream --fillers --server ws://$LAPTOP_IP:8770 --agent-url ws://$PI_V4:8781 --play-remote ws://$PI_V4:8780` (`talk.sh:24-28`). **Required fix:** `Session.run_wavs` (`doc_chat/__main__.py:1021-1037`) calls `self.handle()` instead of `self.respond()`, leaving `_turn_fillers`, `_answer_started`, and `_filler_timer` uninitialized — route `run_wavs` through a non-barge-in `respond_wav()` helper that starts `_filler_timer` and resets per-turn markers.
   - **Mode B (Acoustic/loopback through Pi VAD, 20-Q calibration check):** Play WAVs into the Pi mic with `src/bench/analyze.py` chirp alignment + `StageLogger` (`src/voice_agent/telemetry/events.py`) to measure real VAD endpoint hold (`~500–800 ms`) and add it as an explicit offset report alongside Mode A (since `hear_wav` sends `FinalizeMessage` immediately at WAV EOF, `speech.py:350-351`).
3. **ASR vocabulary:** Build per-dataset entity file via `scripts/make_entities.py --db <docs.db> --merge config/entities.json -o config/entities-bench.json` (and fix `talk.sh:24` `--slot "doc+term?"` -> `"doc+name+acronym+id+term?"`, since `vocab_from_db.py:66-74` emits `name`/`acronym`/`id`).

- **ASR WER:** `turns.jsonl` already stores `raw_text` (Parakeet raw) and `heard` (post-repair) at `doc_chat/__main__.py:973-975`. Compute normalized word-level Levenshtein WER (`raw_wer`, `repaired_wer`, plus entity-token recall) against the dataset's written `question` string. No extra ASR call needed.
- **Pi CPU, RAM, Temperature:** Reuse **`src/voice_agent/telemetry/pi_health.py`** verbatim as a sidecar during Pi runs: `.venv-mcp/bin/python -m voice_agent.telemetry.pi_health --out out/pi_health/<run>.jsonl --pid $(cat /tmp/pi_agent.pid) --interval 0.5`.

Report per-run peak temp, throttling bitmask (`0x0` required for valid latency), median/p95 CPU%, min `MemAvailable` MB, and max `agent_server` RSS MB (note: also log MCP child PIDs or sum process-group RSS so `docs.py` SQLite memory is counted).

  - **Use the local Qwen relay (`Qwen/Qwen3.8-27B`, `http://127.0.0.1:18080/v1`) via `scripts/judge_eval.py`**, NOT Gemini API. ## 5. Feasibility, Sample Sizes & Wall-Clock Cost Table

**Statistical sizing:** For accuracy (binomial $p \approx 0.5$, 95% Wilson CI), $n=150$ gives $\pm 8.0\%$ and $n=200$ gives $\pm 6.9\%$ (with $\ge 25$/stratum across 5–6 categories). For latency **p95**, nonparametric order-statistic stability requires $n \ge 60$ (at $n=60$, 3 turns sit above p95 and $P(\max < \text{true } p_{95}) = 4.6\%$; at $n=80$, 4 turns sit above p95; `src/bench/analyze.py:84`'s `n < 20` check is too small for p95).

**Timing basis from earlier Pi runs (`VERIFIED`):** `REPORT7.md:6,8,23` (`1421c7c`, 387 files / 78.6 MB): ingest **271 s cold / 137 s warm** (99 MB peak RSS); text median first answer **1.33 s**, max **3.79 s** (`REPORT6.md:11` / `FROZEN-ADVERSARIAL-CRITIQUE:7`: mean **3.41 s**, max **8.12 s** on traps; `REPORT5.md:16`: 1.33–1.48 s median). Adding pure-audio overhead per turn (~5 s question WAV + ~1.2 s STT pause/finalize + ~2.5 s agent/TTS + ~7 s answer playback + ~2 s gap) gives **~18 s/turn wall-clock** (budget **20 s/turn**).

### What I Would NOT Do (and Why)
1. **Do NOT run full datasets (2,547 Qs) through live Pi audio:** Takes ~14+ hours, risks thermal throttling and Gemini quota limits, and buys <2% tighter CIs over 60–80 Pi audio Qs + 150–200 offline text Qs.
2. **Do NOT use Gemini to judge Gemini:** ME4's answerer is `gemini-3.1-flash-lite`; using Gemini as judge introduces self-preference bias and unnecessary API spend when local Qwen3.8-27B logprob judging (`scripts/judge_eval.py`) is free and deterministic.
3. **Do NOT include `.odt` in FRAMES before adding an `.odt` reader:** `docindex.py:99-131` explicitly excludes `.odt`; testing `.odt` today only re-confirms `REPORT6.md:19` (0% recall + web hallucination). Either keep `.odt` as a small 5-file "honest unsupported-format refusal" check, or implement T8 first.
4. **Do NOT run FRAMES with live web search enabled:** Because FRAMES comes from Wikipedia, `agent_server.py:925-945`'s web fallback will answer missed local files from Google Search, invalidating file-reading measurement.
5. **Do NOT run MiMoTable `Edit` / `Visualize` prompts or MMLongBench-Doc chart-only questions as undifferentiated accuracy:** ME4 has no spreadsheet-editing tool and no VLM/vision pipeline; report **in-scope accuracy** alongside **overall benchmark ceiling** so headroom vs architectural gaps stay clear.
6. **Do NOT run acoustic room-mic playback for all 200 Pi turns:** Use Mode A (paced WAV -> STT -> Pi Agent -> TTS -> Pi Speaker) for the 200 turns and Mode B (acoustic + Pi VAD) on a 20-turn subset to measure the VAD endpoint offset without room-noise flakes.

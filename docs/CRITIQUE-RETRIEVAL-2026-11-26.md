# Retrieval critique (2026-11-26)

Scope: adversarial review of the current retrieval and grounding path for the ME4 Pi release, based on the current `qwen/ingest` tip (`8dbc4e3`), Pi rehearsal reports 3 and 4, the handoff, RAG experiment log, and source. The Fable planning files and the cluster `.scratch/rag-research` notes named in the handoff are not present in this checkout, so I treat their claims only as summarized by the handoff. No code was changed and no tests, paid calls, or sealed-set access were run for this review.

## Assessment

The dominant remaining risk is **evidence selection and evidence interpretation**, not the FTS5 engine's speed. The Pi fetched and indexed 13,898 chunks from 48 files in 121 seconds, used 138 MB peak RSS during ingest, had 2.677 GB available after startup, and reported no thermal throttling. The pre-fix rehearsal had wrong-path turns: Texas census data fell through to web; a general lane claimed the indexed folder was empty; and "next year" returned the 2026 value. Post-234 recheck improved the hint score from 12/16 to 14/16: catalogue and calendar enumeration now return content, and Texas population is answered from the spreadsheet. The remaining temporal and calculation/doc+web cases show that ranking is only part of the end-to-end outcome; the base-schedule turn also varied between runs. This is evidence that 234 fixed the general-lane wire-format issue, but it does not close temporal grounding or response stability.

## Implemented, rejected, and still open

### Implemented

- `DbIndex.search` ranks FTS5 results and expands candidate limits only when caps leave the requested `k` unfilled ([`dbindex.py`](../src/voice_agent/rag/dbindex.py#L243)). Its result selector caps repeated same-file chunks, permits score-qualified overflow, and suppresses highly similar cross-file chunks ([`docindex.py`](../src/voice_agent/rag/docindex.py#L2753)). The production `search_docs` tool clamps `top_k` to 1–8; the file-context path instead requests up to 300 ranked chunks ([`docs.py`](../src/voice_agent/mcp_servers/docs.py#L224), [`dbindex.py`](../src/voice_agent/rag/dbindex.py#L385)).
- For file-context retrieval, the first `n_files` encountered in the ranked list win; small files are expanded to all chunk text, while large files get optional grep lines and up to `per_big` ranked chunks ([`dbindex.py`](../src/voice_agent/rag/dbindex.py#L399)). Defaults are three files, 15,000 characters for whole-file expansion, four chunks per large file, 20 grep lines, and `rank_k=300` ([`dbindex.py`](../src/voice_agent/rag/dbindex.py#L385)).
- The Gemini answer path checks that a quote occurs in provided passages, checks answer names/numbers, quote length, question overlap, directive text, named-file constraints, and ordinal questions over record files ([`doc_answer.py`](../pipeline/src/voice_pipeline/doc_answer.py#L652)). The `key_absent` check rejects answers when a question key is absent from the cited file; `ROW_KEY_CHECK` remains false ([`ask_documents.py`](../pipeline/src/voice_pipeline/ask_documents.py#L316), [same file](../pipeline/src/voice_pipeline/ask_documents.py#L681)).
- General catalogue/enumeration results and per-file existence checks now decode either a Python list or concatenated JSON objects delivered as an MCP string ([`doc_answer.py`](../pipeline/src/voice_pipeline/doc_answer.py#L447), [`agent_server.py`](../pipeline/src/voice_pipeline/agent_server.py#L722), [same file](../pipeline/src/voice_pipeline/agent_server.py#L750)). This is the concrete 234 fix. Its unit test covers list, concatenated objects, JSON array, malformed string, and `None` ([`test_doc_answer.py`](../pipeline/tests/test_doc_answer.py#L965)). Pi REPORT4 re-ran the same 48-file index on 234: the overview now answered with 48 files / 30 folders, academic-calendar enumeration returned six real filenames, and the Texas population route changed from web to docs/accepted. Total hint score rose to 14/16 from 12/16 in REPORT3. The folder count was unchecked by the operator, so it is not ground truth validation.

### Rejected or deferred with useful measurements

- Raising/lowering file chunk caps was flat across 14 configurations, with at most one row gained and several configurations losing rows. Keep current values unless a new error analysis identifies a targetable failure class. The second-stage lexical reranker is a clear negative result (baseline 92/112 hit@4 vs 81–87); do not revive it without a different candidate-generation/feature hypothesis. These are E9b/E9c in [`RAG-EXPERIMENTS.md`](RAG-EXPERIMENTS.md#e9-pdf-diagnosis-2026-11-20-scripts-in-scriptsexperiments).
- The row-key guard is appropriately disabled: the first broad version rejected 44 correct rows, and narrowed variants still lost correct cases while gaining little. The current Pi trap d10 also demonstrates that exact citation/number checks do not establish row semantics. Do not turn it on globally; evaluate a carefully delimited rule against held-out traps and ordinary table rows.
- Hybrid (BM25 + ColBERT late interaction) gained 6 net external-set hits@4 (7 gained, 1 lost), primarily paraphrases, but used 1.85 GB peak RSS and took 17m52s to first build over 13,780 chunks on the laptop. It is not suitable for this Pi deployment. The paper supports late interaction's quality/efficiency trade-off in its own evaluated setting, not this Pi's RAM/time budget; local measurements govern here ([ColBERT](https://arxiv.org/abs/2004.12832), [local E10](RAG-EXPERIMENTS.md#e10-hybrid-retriever-vs-fts5-on-the-external-set-2026-11-20)).
- The proposed static embedding arm remains an experiment, not an established optimization. Its acceptance targets (recover at least 4 of 6 hybrid gains, <150 MB, <50 ms/query on Pi 4) are reasonable hypotheses, but must be measured on the same device and paired set. BEIR's broad evaluation found BM25 robust and late-interaction / reranking effective but costly; it does not imply that a small static model will recover this corpus's paraphrase gains ([BEIR paper](https://arxiv.org/abs/2104.08663)).
- The Gemini validation memo's broad advice to add header prepending and reranking is not sufficient evidence for this corpus. The local experiments already show one strong table-specific improvement in docx structure, but also show that a generic lexical reranker regressed hit@4. Likewise, vendor-reported table gains should motivate a local ablation, not be treated as expected Pi gains. Table-specialized retrieval papers address complex table reasoning and often change the task (SQL/multi-stage QA), beyond this Friday voice lookup scope ([TableRAG, EMNLP 2025](https://aclanthology.org/2025.emnlp-main.710/), [local E8/E9](RAG-EXPERIMENTS.md#e8-spike-2a-docx-tablesstyles-html-over-pruning-and-the-matcher-2026-11-20)).

## Failure analysis: wrong row vs missing evidence

The validator's core invariant is quote containment: the quoted evidence must occur in text returned by retrieval. That verifies provenance for the quote, but it is not a complete factuality guarantee and does not establish that every answer claim follows from it. It cannot distinguish a true answer from the wrong row when both the wrong value and the requested entity are nearby in the same passage. `names_numbers_ok` checks supported names/numbers, and the per-file key check establishes that a key appears somewhere in the cited file; neither demonstrates that the key/value relationship is correct in the cited row. This matches the logged Pi outcome: the GS-15 step comparison was arithmetically right but failed a check and spilled into `search_docs`; a wrong-source or near-row answer can still be accepted if its quote and terms pass.

The extraction/retrieval benchmark also has a known blind spot: the handoff says wrong-row traps t04–t06 are not measured offline because the oracle quotes the correct row even when the model answer is wrong. Therefore current aggregate hit@k is not evidence that row grounding is safe. Create trap examples where retrieval returns the correct *file* and answer-like *nearby row*, but a wrong row/value would satisfy the current coarse checks. Score at least four separate outcomes: correct row in candidate context; correct row in final bounded context; accepted answer correct; wrong answer accepted. Keep abstention distinct from a miss and from an incorrect web fallback.

### Targeted experiments and gates

1. **Held-out row-grounding replay (offline, no model call).** Build a fixed set of confusable table rows from already permitted public/dev data: same location/month but another customer type, same grade but another step, adjacent states, and same key under another year. For each, record file, row/cell coordinates, query, correct answer, and a distractor answer from the competing row. Run both `search_docs` and `file_context`; report whether the right row is present in top 4 / final context and whether a scripted answer-shaped distractor passes `judge`. Gate: zero wrong-row scripted answers accepted; report correct-answer acceptance separately (target no more than one lost existing correct row). Split fixture construction from tuning so thresholds are not selected on the held-out rows.
2. **234 Pi integration regression.** The initial recheck has been done: the real Pi path answered “What are all the files about?” and “Which files are academic calendars?” and retrieved the Texas value from `nst_est2024_pop.xlsx`. Gate the follow-up by checking catalogue count against SQLite, calendar result against the seven-file expected list, and repeating the turns across cold and warm starts. Preserve audio route and command behavior. This closes the specific report defect, not a general retrieval ranking improvement.
3. **Wrong-row mitigation ablation.** Compare current validator vs (a) existing key_absent only, (b) a narrowly scoped table-row key/value co-occurrence check for single-row numeric comparisons, and (c) abstain/fall-through when the quote mentions multiple competing values for the same key. Use same answer candidates, corpus, and token budget. Gate: zero new false accepts on held-out traps, <=1 lost correct answer on non-trap set, and report web fallback correctness separately. Keep the row-key check off unless it passes.
4. **Lexical recall diagnostics before new ranking.** On the fixed external 112-row set, capture answer-bearing chunk rank (not only file rank), query-token coverage, and whether answer text is absent from the index. Stratify paraphrase, numeric/table, identifier, and broken-word rows. Gate any ranking change on paired hit@4 (tokens), with no more than one answerable row lost and gains concentrated in the predeclared target bucket; also report MRR and latency. The existing E9a diagnostic found 7/9 PDF misses had the right file in top four while answer-bearing chunks were buried, so per-file routing alone is not enough.
5. **Budget ablation for `file_context`.** With identical `rank_k=300` candidates, compare current whole-small-file plus grep/chunk assembly against bounded candidate-only passages and one modest larger lexical pool. Cap every arm to equal total chars/tokens, and retain only within-source ordering metadata. Measure answer-bearing context recall, answer correctness/false accepts, context size, latency, and peak RSS on Pi. Gate: no regression in honesty traps; improve correct answers on at least two predeclared misses or reject the change. Do not infer from a larger context alone: additional rows can help recall and increase near-row confusion at once.
6. **Defer semantic arm until after release.** If Pi time permits later, test FTS5 vs static embeddings vs RRF with identical preprocessing/context budget, then compare against laptop hybrid. Gate as proposed in E10's open hypotheses: recover >=4 of 6 hybrid hit@4 gains, <150 MB incremental/total stated clearly, <50 ms query on Pi 4, and no increase in accepted wrong-row answers. RRF is a fusion method, not a guarantee; its classic result aggregates rankings from the studied systems, so test rank diversity and retain the lexical-only control ([RRF paper](https://doi.org/10.1145/1571941.1572114)).

## Ranking and lexical notes

- FTS5 is a good engineering choice here: SQLite's official documentation confirms BM25 column weights and rank ordering support, including configurable column weights and a faster hidden `rank` column. That establishes implementation capability; it does not prove an alternate weight improves this collection. The current project has already found FTS5 and rank-bm25 broadly tied on its fixture and public benchmarks. Any weight/tokenizer change should therefore be a paired local experiment ([SQLite FTS5 docs](https://www.sqlite.org/fts5.html), [E3/E11](RAG-EXPERIMENTS.md#e3-alternatives-to-bm25-storage-2026-11-19)).
- `grep_terms` drops a stop list, truncates each query token to five characters, deduplicates on that prefix, and `grep_lines` treats a substring occurrence as a match ([`dbindex.py`](../src/voice_agent/rag/dbindex.py#L83)). This is cheap but can conflate terms sharing a prefix (and can match an identifier fragment); its ordinal mode also retains first and last high-scoring lines. It is context assembly, not a calibrated relevance scorer. Add targeted collision tests/evaluation before relying on it for table cells; preserve original line order in delivered excerpts.
- The local external-set result is 92/112 hit@4 under converter-independent `tokens`, 80/112 under strict `normalized`, while hybrid was 98/112 tokens. The difference between matchers is partly anchor-format bias, not necessarily missing evidence; do not use normalized alone to choose converters. Conversely, `tokens` is not a semantic correctness metric and cannot reveal wrong-row answers. Preserve both and add the answer-level measures above.

## Device and release constraints

The handoff describes a pure-audio evaluation: Pi runs VAD and the agent/MCP stack; speech recognition and synthesis remain on the external laptop speech server. Retrieval additions therefore compete with agent memory, first-audio latency, and available time on a 4-core, 4 GB Pi, even when the retrieval DB itself is small. Current report has 2.677 GB free after stack startup and `throttled=0x0`; no post-234 audio verification exists. Keep Friday changes to correctness fixes demonstrated through the end-to-end path. Do not run full RAG benchmark matrices or introduce semantic dependencies during the freeze.

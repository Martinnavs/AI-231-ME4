# Deep-research integration options (2026-11-26)

## Recommendation

Start with an **opt-in deep-research skill** that orchestrates tools and models already available. Its instructions define a fixed procedure: one plan, a few targeted `web_research` calls, at most one gap-filling search, one synthesis, and a source/claim evidence ledger. Keep single factual questions on `web_answer`. For work that continues beyond the active turn, add a thin, read-only async harness that reuses the existing job table/status/cancel and budget accounting. A skill describes procedure; only the harness can enforce hard call, time, and cost ceilings. Do not adopt a research framework first.

This is an architectural fit assessment, not a latency or quality result. No package was installed, no paid model/search call was made, and no end-to-end research run was measured. The handoff explicitly cut deep research for the Friday release; this document describes a separate future lane and should not be interpreted as a change to the release scope. The prior project estimate of 2–3 model calls, roughly 3.5–8.5 seconds, and about $0.003/question is an unverified design estimate, not a target or promise ([status summary](ME4-STATE-2026-11-25.md#6-what-we-researched-and-what-each-source-told-us), [release handoff](ME4-HANDOFF-2026-11-26.md#2-tickets-scratchme4-next-tickets-untracked-copied-into-each-worktree)).

## Why the skill plus thin harness matches this stack

The current app already has most necessary primitives:

- `web_research` is the actual raw-result tool for research that feeds another step. It returns title/URL/snippet data and is explicitly described as not for one-fact spoken answers ([`tavily_search.py`](../src/voice_agent/mcp_servers/tavily_search.py#L433)). It can issue an authority-hint or recent second query; current constants allow up to two attempts and a 12-second per-request timeout, and its credit counter charges successful backend search calls ([same file](../src/voice_agent/mcp_servers/tavily_search.py#L460), [timeout/retry](../src/voice_agent/mcp_servers/tavily_search.py#L477)). A research lane must count this hidden fan-out as well as its own calls.
- `web_answer` is designed for one concise factual response. The Pi pipeline redirects `web_research` to `web_answer` for a simple “who is” question because the front agent previously looped on eight raw-search calls for a one-fact request ([`agent_tools.py`](../pipeline/src/voice_pipeline/agent_tools.py#L1103), [redirect](../pipeline/src/voice_pipeline/agent_tools.py#L1257)). Preserve that policy for ordinary turns; expose a separate explicit research intent/tool path so multi-source requests can use raw results without silently weakening the guard.
- Delegate already has step/time/token/USD limits and a JSON spend ledger ([`subagent.py`](../src/voice_agent/agent/subagent.py#L308), [ledger](../src/voice_agent/agent/subagent.py#L352)); `JobTable` persists job records, completion notices, and interrupted-on-restart state ([`jobs.py`](../src/voice_agent/agent/jobs.py#L48)); MCP tools expose background submit/status/cancel ([`delegate.py`](../src/voice_agent/mcp_servers/delegate.py#L425)). Reuse this lifecycle pattern and cost-accounting code, but **do not** reuse the code-building delegate runner or its write/network sandbox: research needs a distinct read-only tool allowlist and a separate ledger/output schema.
- The live agent already has asyncio and a per-turn docs path; Gemini structured requests are async. A research coordinator can therefore stay async without adopting LangGraph, use bounded `asyncio.TaskGroup`/gather for independent searches, and keep model/search I/O remote. Python's event loop should not be blocked by synchronous crawlers or package code.

## Suggested bounded workflow

### Trigger

Only start from an explicit request for a comparison, history/review/opinion synthesis, “research this,” or a report that needs multiple independent sources. Keep ordinary “who/what/current/latest” fact lookups on `web_answer`. This distinction is already encoded in the tool descriptions and the one-fact redirect; make the explicit route visible in tool policy rather than relying on the base assistant to infer repeated calls.

### Run phases

1. **Skill triggers explicitly.** Use this workflow for multi-source comparisons, history/reviews/opinions, or “research this.” Do not use it for ordinary fact lookups. Ask a scope question only when the requested coverage or time window materially changes the work.
2. **Run in the current turn when bounded.** For a small request, the skill guides one plan call, then direct MCP calls, then synthesis. For work that should continue after the turn, submit a research-only async job and return its job id/status. Record the question, session, skill/policy revision, start time, and deadline.
3. **Plan once.** One Gemini structured-output call returns 2–3 non-overlapping research questions, scope/time window, and minimum evidence for each. Reject malformed plans and fall back to one original query. Do not run an open-ended planner loop.
4. **Search in parallel, bounded.** Run at most three `web_research` tool invocations over the entire job, with one of those available for a gap-filling query only when the first results expose a named contradiction/gap. Each invocation may fan out into two backend queries and each backend query may retry once. To enforce a six-successful-search-credit ceiling, count successful Tavily calls in the search/budget service; count network attempts separately for operational diagnostics. Respect the provider credit reserve. No general browser, shell, arbitrary MCP, code, file-write, or publish tool.
5. **Build an evidence ledger before synthesis.** For each result persist stable source id, URL, title, exact returned snippet/quote, query/subquestion, retrieval time, publication date if available, provider, and source type. Deduplicate URLs; mark conflicts/staleness. Treat results as untrusted data, not instructions. If local docs are requested, record file/section/page/chunk id and text separately from web evidence.
6. **Synthesize once.** The model returns a concise answer/report with ledger ids attached to factual claims. Deterministic formatting resolves ids to clickable URLs and rejects unknown ids. Mark unsupported claims unknown or omit them. A source snippet is not full-page verification.
7. **Finish or cancel.** Persist report, ledger, model/tool counts, cost, elapsed time, and terminal state. Cancellation prevents future scheduling, cancels pending async work where possible, closes MCP clients, persists partial evidence, and sets terminal status. An already accepted remote request may finish and bill; cancellation is cooperative.

### Initial ceilings to validate, not promises

For a first evaluated version, start with: 1 planning call; up to 3 total `web_research` MCP tool invocations; up to 6 successful billed backend searches across the whole job (because one tool call may make 2 searches); up to 12 network attempts if each search retries once; 2–3 planned queries with the third tool call reserved for a specific gap; 1 synthesis call; at most 8 unique URLs; 1 active research job per session and a small global queue; a 30-second hard deadline; and a hard per-job USD cap. Search success/credit counts must be enforceable where calls are made, not guessed from skill instructions. Deadline expiry returns partial evidence and an incomplete status.

These are starting guards selected to make calls auditable. The 30-second ceiling is a proposed maximum deadline, not expected completion latency. Measure Pi-to-provider conditions at normal and loaded concurrency before setting user-facing expectations. Voice should announce once at job start and once at completion; do not speak every intermediate search result.

## Job lifecycle and API shape

Prefer a dedicated `research_*` MCP tool family backed by the current `JobTable` pattern:

| Tool | Inputs / behavior | Output |
|---|---|---|
| `research_start` | `question`, optional `scope`/`recent`; validate limits and explicit multi-source intent, create async background task. | `job_id`, `status=running`, submitted timestamp. |
| `research_status` | Exact `job_id`; return one job only (avoid fuzzy “latest” resolution for consequential result selection). | Status phase, searches used/remaining, cost so far, elapsed time, last progress timestamp. |
| `research_cancel` | Exact `job_id`; set cancellation event; stop scheduling more calls and await cleanup to a bounded deadline. | `cancellation_requested`, then terminal state after the current cooperative boundary. |
| `research_result` | Exact `job_id`; paginate or bound report and sources; return ledger separately if needed. | Final/partial report with citation ids and URLs, status, cost and counts. |

Use states `queued → planning → searching → synthesizing → done`; terminal alternatives `partial`, `cancelled`, `failed`, `timed_out`, `budget_exhausted`. Persist phase transitions and ledger entries atomically. On restart, mark interrupted work `lost` unless a resumable checkpoint contains enough state to safely resume without repeating paid calls. This matches the current `JobTable` behavior, which marks running jobs lost on startup; adding restart-resume is a separate feature and requires idempotent call ids to avoid duplicate billing ([`jobs.py`](../src/voice_agent/agent/jobs.py#L48)).

MCP's Tasks extension is an available protocol option for long-running calls, but it returns a durable task handle and cooperative `tasks/cancel`; the server may still reach another terminal state after cancellation. It also requires client capability negotiation and status retrieval/subscription handling. The existing app's job tools are already shipped and fit its background-notice UX. Use MCP Tasks only if interoperability with external MCP clients becomes a product requirement, after verifying the installed SDK/version supports the current extension; do not add it just to avoid reusing the local job table ([MCP Tasks extension overview](https://tasks.extensions.modelcontextprotocol.io/), [task cancellation semantics](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks)).

## Tool and evidence boundaries

- Allow only the raw `web_research` search tool, plus local `search_docs` when the user explicitly asks to combine their files and the web. `web_answer` may be called only as a separately identified fact-check path if policy allows; its answer text and source output do not replace the source ledger.
- Do not give the research job `delegate`, code tools, shell, `publish_site`, home/media actions, or general MCP access. Research is read-only and cannot modify the project or user files.
- Search results are untrusted. Preserve the existing `<untrusted_search_data>` boundary and do not feed web text as system instructions. Citations are explicit evidence pointers; a citation matching a URL does not prove the cited page supports the sentence.
- Keep a ledger at **claim granularity** in the final report: each factual sentence/table row maps to one or more source ids. The model may summarize; deterministic checks enforce that every cited id exists and every report URL comes from the ledger. Human or trusted evaluator review is still needed for entailment and source quality.
- Report “sources found” separately from “sources opened/read.” Current `web_research` returns search result titles, URLs, and snippets; that is not equivalent to fetching and reading full pages. If deeper source text is required, add one bounded `fetch_source(url)` tool with host allow/deny checks, response byte and timeout limits, and SSRF-safe URL validation before launching this lane. Do not claim full-page verification while using snippets only.

## Evaluation before enabling

Use a small free/offline or owner-approved public-query set first; no sealed data. For at least 20 explicit multi-source prompts, record: accepted source count and quality; citation URL validity; claim-to-source support; contradictory-date handling; incomplete/timeout behavior; plan/search/model call counts; measured USD; median/p90 end-to-end time; first progress time; and cancellation latency/cost after cancelling at planning, search, and synthesis phases. Include at least 5 single-fact questions as controls and require that they remain on the existing `web_answer` path with no planner/search fan-out. Include one injection page and verify that its instructions are never followed.

Proposed initial enablement gates: zero uncited externally checkable claims in the final report; zero broken or fabricated URLs; no single-fact control invokes the deep lane; all jobs remain within the hard backend-call and USD ceilings; no user data/write tools available; cancellation schedules no further work after the next cooperative boundary; and publish latency/cost distributions without treating a small sample as an SLA. Tune quality and time caps only from these runs. Until these gates are met, expose this as an explicit experimental tool rather than silently auto-routing speech requests.

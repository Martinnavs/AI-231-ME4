## Findings to act on experimentally

1. **XLSX is the clearest memory/latency optimization candidate.** `read_xlsx` correctly uses openpyxl's lazy `read_only=True` mode, but `_render_xlsx_sheet` retains both raw and rendered versions of every row up to 20,000 rows, then renders the table into Markdown; the input bytes are also held by the caller. See [readers.py:343](../src/voice_agent/rag/readers.py#L343), [readers.py:354](../src/voice_agent/rag/readers.py#L354), [readers.py:472](../src/voice_agent/rag/readers.py#L472), [readers.py:493](../src/voice_agent/rag/readers.py#L493). Openpyxl's own docs describe read-only iteration as lazy/near-constant memory and require `close()`, which this reader does in its finally path; but the application-level row lists defeat constant-memory behavior. A low-risk experiment is stream table rows into bounded output while retaining only the at-most-15-row header-detection window and required merged-header state. Preserve full existing row/header golden coverage. **Pi cost:** likely useful on very large sheets; not expected to change the 116 s/44-file Pi ingest unless XLSX is a material share. Measure peak RSS and XLSX wall time independently before changing architecture.

2. **PDF engine choice has already delivered the strongest measured optimization; validate current hardware and extraction quality, do not reopen the old x86 comparison.** The current code chooses pdfium when installed (`auto`) and falls back to pypdf; per-page handles are closed. See [docindex.py:1435](../src/voice_agent/rag/docindex.py#L1435), [docindex.py:1450](../src/voice_agent/rag/docindex.py#L1450), [docindex.py:1494](../src/voice_agent/rag/docindex.py#L1494). The prior experiment log reports 15–23x faster x86 extraction and 36/36 PDF anchors preserved, but explicitly says Pi time was projected, not measured. Pi's earlier pypdf baseline was 59.3 s for the 126-page IRS instructions, 19.0 s Pico sheet, 13.2 s Pub 15 ([RAG-PI-RESULTS.md](RAG-PI-RESULTS.md), PDF findings); the latest handoff reports 116 s for 44 files, but does not break current PDF-engine time down. Measure fresh-file per-PDF timing, peak RSS, and anchor parity on the Pi with both engines. pypdfium2 docs warn `get_text_range` Unicode behavior has version-sensitive UCS-2/bounded semantics; current auto path should be evaluated with non-BMP and unusual Unicode anchors too ([pypdfium2 API](https://pypdfium2.readthedocs.io/en/stable/python_api.html)).

3. **Large-file peak memory is a concrete risk at existing caps.** `load_file` reads any supported file up to 64 MiB fully into `raw_bytes`; that data is passed into parser work, and XLSX/PPTX readers then wrap those bytes in `BytesIO` / open package structures ([docindex.py:466](../src/voice_agent/rag/docindex.py#L466), [docindex.py:480](../src/voice_agent/rag/docindex.py#L480), [readers.py:493](../src/voice_agent/rag/readers.py#L493)). The warm worker path is bounded by a worker memory limit only when configured; default is 0 (no explicit RLIMIT_AS) ([ingest.py:529](../src/voice_agent/rag/ingest.py#L529), [ingest.py:979](../src/voice_agent/rag/ingest.py#L979); see also [ingest_workers.py:18](../src/voice_agent/rag/ingest_workers.py#L18)). Do not simply raise worker count: each worker can expand a compressed office file into Python object graphs. The experiment should use the Pi's 4 GB budget, cgroup/OS peak RSS, and adversarially large-but-valid workbook fixtures. Expected benefit is robustness, not faster normal corpus ingestion.

4. **Instrument phase costs before tuning the ingestion pipeline.** The 44-file Pi run is 116 s per the current handoff, but the current report does not provide a current per-format breakdown. The prior Pi report showed large PDFs dominated by extraction (pypdf 94–98% of file time) and office/html work dominated by isolated child startup/import; this supports separating PDF, XLSX, and process startup timings rather than generic “ingest speed” comparisons. Existing command path parses changed files in workers and commits file/chunk rows while collecting results ([ingest.py:962](../src/voice_agent/rag/ingest.py#L962), [ingest.py:979](../src/voice_agent/rag/ingest.py#L979), [ingest.py:1051](../src/voice_agent/rag/ingest.py#L1051), [ingest.py:1122](../src/voice_agent/rag/ingest.py#L1122)). For a separate research run, log per-kind parse, chunk, SQLite write, and FTS-build elapsed time plus whole-process max RSS. The planned 160 MB/509-file Pi run in handoff is the relevant throughput sample; its reported budget is under 50 min and ~2.5 GB RSS, not a measured outcome.

## Existing ideas and decisions (do not count as new)

- **Fable:** the available handoff summarizes Fable's edge validation, Pi rehearsal, and paid answer rounds. It does not contain a new extraction optimization proposal. The original plan files are not present, so no stronger attribution is supportable.
- **PDFium:** already merged and measured on x86. The open question is Pi timing/quality, not whether to adopt it anew. Prior log says external retrieval gained no hit losses and one gain; Pi timing remained pending ([RAG-EXPERIMENTS.md](RAG-EXPERIMENTS.md), E12).
- **XLSX stacked headers:** existing experimental feature (`VOICE_AGENT_RAG_TABLE_HEADERS=stack`) with table-header and cover-sheet logic, not a new optimization. Experiment log parks xlsx merged/multi-level headers as low-value under the current tokens matcher; handoff also records that header stacker was cut for Friday. Do not re-add based on generic vendor claims.
- **Incremental FTS merge tuning:** the Gemini validation document suggests disabling FTS5 automerge during bulk ingest then restoring it, but this branch uses FTS5 and code should be checked before treating the suggestion as applicable. SQLite says FTS5 commits create segment b-trees and automerge trades write time for future search cost; optimize merges the whole index and can take a long time ([SQLite FTS5 docs](https://www.sqlite.org/fts5.html)). Existing experiment log reports `fts_optimized`/no-optimize support. This is an ingestion/write-vs-first-query tradeoff, not a parser speedup. Measure on the actual 509-file set; never assume a speedup from the generic recommendation.
- **Header-prepended chunks, RRF/hybrid, graph indexing, contextual retrieval:** Gemini's cited recommendations primarily target retrieval and enterprise-scale semantic systems. Current ME4 is lean FTS5, capped to few chunks per file, and has no dense hybrid arm. They do not address parse wall time and are not appropriate “extraction optimizations.” Handoff explicitly cuts graph variants, rerankers, embeddings, and row-key guard for production.
- **Archive ingestion:** the current zip-to-folder runbook is already measured at 48 files / 13,898 chunks / 18.5 s (handoff, commit `f82a06a`). The wrapper extracts before normal folder ingestion, so zip extraction and ingest should be timed separately if diagnosing future delays. Existing zip protections should not be weakened for throughput.
- **OCR:** current OCR is a bounded second phase, with a total deadline and 30-second per-image join, then streaming FTS sync ([ingest.py:112](../src/voice_agent/rag/ingest.py#L112), [ingest.py:147](../src/voice_agent/rag/ingest.py#L147), [ingest.py:200](../src/voice_agent/rag/ingest.py#L200)). The handoff's earlier production checklist has Tesseract present. More OCR engines/layout ML would raise install size, RAM and CPU use, and no supplied Pi evidence shows it pays off for the current corpus. Keep it as a targeted scanned-page experiment, not a global pipeline change.

## Code-grounded failure modes and cost model

- **Mixed native/scanned PDFs can lose their scanned pages.** Both pypdf and pdfium classify a document as scanned only when more than half of pages are sparse; when at most half are sparse, only non-sparse pages are returned ([docindex.py:1415](../src/voice_agent/rag/docindex.py#L1415), [docindex.py:1428](../src/voice_agent/rag/docindex.py#L1428), [docindex.py:1459](../src/voice_agent/rag/docindex.py#L1459), [docindex.py:1487](../src/voice_agent/rag/docindex.py#L1487)). This is a real extraction completeness gap if the image detector does not later recover those page images. Test a PDF with one scanned page among several born-digital pages and assert that page has an OCR image record/chunk. This is a correctness experiment, not a speed optimization.
- **XLSX style/used-range metadata can inflate work or cut off valid rows.** openpyxl explicitly says read-only mode trusts producer-supplied worksheet dimensions and offers `reset_dimensions()` for incorrect dimensions ([openpyxl optimized modes](https://openpyxl.readthedocs.io/en/latest/optimized.html)). Current reader stops at 20k rows and 200 columns; these are intentional caps ([readers.py:32](../src/voice_agent/rag/readers.py#L32), [readers.py:354](../src/voice_agent/rag/readers.py#L354)). A fixture with bad dimensions could validate whether iteration is unexpectedly truncated or excessive. Any reset policy needs hard bounds to prevent hostile dimensions from turning into unbounded work.
- **Worker parallelism is capped at three, but the RAM heuristic is coarse.** `_auto_workers` uses available RAM minus 800 MB, allocating one worker per 600 MB up to three ([ingest.py:397](../src/voice_agent/rag/ingest.py#L397)); it cannot account for format-dependent expansion, model/server co-load, or shared filesystem cache. Python multiprocessing docs also note process startup/resource tracking costs vary with start method ([Python multiprocessing docs](https://docs.python.org/3/library/multiprocessing.html)). Since the Pi already runs ME4 services during rehearsal, benchmark `workers=1` vs `auto` with the agent running and compare wall time, peak RSS, swap, and throttling. An apparent laptop win is not evidence of a Pi win.
- **Deadline is a skip governor, not a hard wall-clock interrupt for every work unit.** The handoff says worker parser timeouts are 300 s by default; deadline checks are made around dispatch/collection ([ingest_workers.py:94](../src/voice_agent/rag/ingest_workers.py#L94), [ingest.py:969](../src/voice_agent/rag/ingest.py#L969)). A parser on a large file may therefore consume its per-file budget despite a shorter overall deadline; report skipped files and status, not just elapsed time.
- **Expected Pi cost:** distinguish hosts and runs: 116 s is the earlier 44-file Pi ingest; 18.5 s is the handoff’s 48-file wrapper measurement, not the current Pi result. REPORT3 measures the actual 48-file Pi ingest at 118.8 s (121 s wrapper wall), with 138 MB reported child peak RSS. REPORT4 reuses that index and adds no ingestion measurement. The 160 MB / 509-file test remains a planned owner-side run, with <50 min / ~2.5 GB as its guardrail. Do not extrapolate linearly from file count or bytes: a 126-page PDF previously took about a minute under pypdf while many small files spend time in imports and indexing. Typical user experience is first ingest/refresh cost only; unchanged files reuse prior records and canonical cache (see [ingest.py:850](../src/voice_agent/rag/ingest.py#L850) and [canonical_cache.py:84](../src/voice_agent/rag/canonical_cache.py#L84)).

## Primary-source research notes

- SQLite's FTS5 documentation explains transaction segment trees, the write/read tradeoff of `automerge`, and the full-index cost of `optimize`: [SQLite FTS5](https://www.sqlite.org/fts5.html).
- openpyxl's supported streaming behavior and incorrect worksheet-dimension caveat: [Optimised Modes](https://openpyxl.readthedocs.io/en/latest/optimized.html).
- pypdfium2 API documents text extraction semantics and Unicode caveats: [Python API](https://pypdfium2.readthedocs.io/en/stable/python_api.html).
- Python's official multiprocessing docs describe process contexts and start methods: [multiprocessing](https://docs.python.org/3/library/multiprocessing.html).
